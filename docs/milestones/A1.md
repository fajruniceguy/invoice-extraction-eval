# A1: Breakdown of the `hallucinated_value` errors, and an audit of copies that share a label

Status: spec (written before code; not edited after approval)
Roadmap ref: none (scorecard finding: `hallucinated_value` is 24 of the 323-field `test-final` errors, 27 in `test-g1`);
scope approved by the owner on 2026-10-09

## Goal
Say what the `hallucinated_value` errors ARE: where they come from (fields or row cells; which documents; which labels; what
confidence; what the validators said), and whether the label or the model is the more likely cause, so the scorecard number
can be quoted with its meaning. The first look at `test-g1` found that 11 of the 12 scalar cases sit on three phone photos
(doc_032, doc_033, doc_034) that borrow the blind label of doc_016 (`gt_from`) while the model reads three DIFFERENT receipts
in them (other vendor, date and total each time, none of them the electricity-token bill the label describes). That is a
possible ground-truth lineage error, not a model failure, and it has to be a flagged, reproducible check and not my reading.

## Scope
- `evalkit/hallucinations.py`, offline and deterministic, nothing in it changes a score:
  - `collect(run_dir, manifest_path, labels_dir)`: every `hallucinated_value` of a run, scalar fields and row cells, each with
    the document, its label owner, capture and doc type, the field or cell, the value, confidence, page, the validator codes
    and the model's own free-text note on it, whether the model's raw answer (`parsed`) had the same value, and the
    denominators (labeled-absent scalar fields; compared cells whose label is null) so a RATE can be stated.
  - Row cells use the scorer's own pairing (`match_rows` over the returned rows), so the count equals the scorecard's.
  - `lineage_audit`: for every label shared through `gt_from`, the owner and each member are scored on the labeled non-null
    scalar fields (validated, the scorer's own `score_field`). A member is **suspect** when it has at least 3 such fields, the
    owner has at least 3, and its exact-match rate is at least 0.5 below the owner's (a rule fixed here, before the result:
    the first look showed 0.8 for the owner and 0.2 for each copy). The report also lists, per group, the distinct values the
    run read for `document_number`, `document_date` and `total`: copies of one page should read the same.
  - `to_markdown(report, notes)` (the committed report: counts, rates, tables by level, field or cell, owner, capture and
    confidence band, the lineage table; values appear, evidence quotes do not) and `review_markdown(report)` (a list for the
    owner with the quotes and the model's notes, written only to a path outside `docs/` and `results/`).
- `scripts/analyze_hallucinations.py RUN [--out F] [--review F] [--notes F]`, exit 0 done, 2 unreadable run or labels.
- `docs/eval/hallucinations.md`: the generated tables for `results/test-g1` plus a hand-written reading, finished after the
  owner has looked at the pages in the review list (the owner's findings are written down as the owner's, not mine).

## Out of scope
- Changing any label, `gt_from`, manifest row or the scorer. If the audit is right, relabeling is the owner's decision and
  its own step (`ground_truth/LABELING.md`, a CHANGELOG line, and a record that the new label was made AFTER the model's
  output was seen: it cannot be called blind).
- Changing the extractor, the prompt or the validators; the probe set (S4); viewing any real page (I do not).

## Acceptance criteria
Offline and deterministic.
1. `python -m uv run pytest -q tests/test_hallucinations.py` -> all pass, on a hand-built run (every number worked out in a
   comment above the world that produces it): a scalar and a row-cell hallucination are both found and the totals equal the
   scorer's `hallucinated_value` count for the same run; a wrong value, an abstention and a correct absence are NOT counted;
   the denominators; a hallucination the model also made in `parsed` versus one the validators introduced (none can be: say
   so in a test); the lineage rule at its boundary (a gap of exactly 0.5 is suspect, 0.49 is not; 2 fields is never suspect);
   a group whose copies agree is not suspect; the report holds no evidence quote and the review list does; the review path
   inside `docs/` or `results/` is refused; the report is byte-identical on a second run.
2. `python -m uv run python scripts/analyze_hallucinations.py results/test-g1 --out docs/eval/hallucinations.md` -> exit 0;
   the scalar count is 12, the row-cell count 15, the sum 27 = the scorecard's `hallucinated_value`; likewise
   `results/test-final` gives 12 + 12 = 24.
3. The lineage table flags doc_032, doc_033 and doc_034 as suspect against doc_016 and does not flag doc_016 itself.
4. Mutation pass on the module (`tests/mutants/hallucinations.py`): every mutant killed.
5. `python -m uv run pytest -q -m "slow or not slow"` and `python -m uv run ruff check` -> green (the known flaky
   `test_mutation_check` is rerun alone before it is called a failure).
6. `git status` shows no change under `ground_truth/`, `data/`, `results/`.

## Risks
- The audit is a heuristic on 5 fields; it can be fooled by a copy that is genuinely hard to read -> it only FLAGS, the report
  says "needs a human look at the pages", and the verdict is written by the owner, not by this tool.
- The review list holds quotes from (redacted) real pages -> it goes to `outputs/` (gitignored) and the script refuses a path
  inside `docs/` or `results/`.
- A row-cell "hallucination" can be a row-definition disagreement (fees, vouchers and discounts counted as line items) rather
  than an invention -> the report keeps the model's own note next to each, and does not call them hallucinations on its own.
