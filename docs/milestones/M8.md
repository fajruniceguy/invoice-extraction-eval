# M8: One optimization with measured impact: a resolution and thinking-budget sweep

Status: spec (written before code; not edited after approval)
Roadmap ref: docs/ROADMAP.md#M8

## Goal
A sweep over image resolution and the model's thinking budget runs on the dev split and reports accuracy against
cost and latency, names the chosen setting and why, and any run's scorecard can carry a before/after table against
a baseline run.

## Scope
- Context: the extractor is GLM 5.3 Flash through Command Code's OpenAI-compatible endpoint. Measured on
  2026-10-08: strict `json_schema` is rejected (HTTP 400; the client falls back, and `LLM_STRUCTURED_MODE=json_object`
  skips the wasted request); `reasoning_effort` accepts `off | low | medium | high | xhigh | max` (not `none`); it is a
  reasoning model (about 118 s and 13.5k input tokens for a 2-page invoice). Both knobs are request-time settings
  (`LLM_IMAGE_MAX_LONG_EDGE`, `LLM_REASONING_EFFORT`): the stored pages are never touched and the response-cache key
  includes both, so sweep points cannot contaminate each other. "Token budget" is the thinking budget
  (`reasoning_effort`): output tokens cannot be capped safely on a reasoning model, since a cut JSON is a failure.
- Design: one knob at a time from a baseline, then one confirmatory run of the winning combination. Levels,
  resolution: 1024 px / 1568 px / the stored size (the baseline); effort: off / low / the provider default (the
  baseline). That is 6 runs of the 10 dev documents (baseline, 2 resolution, 2 effort, 1 confirmatory).
  The baseline is an existing run, `outputs/runs/dev-baseline` (production prompt, stored-size pages, default effort).
- The rule for the chosen setting, fixed before any result: among the points with no failed or refused document, the
  cheapest (list-price cost per document) whose accuracy is within `--tolerance` (default 2 points) of the baseline
  AND whose M6 verdict against the baseline is "ok"; ties go to the lower p50 latency; if none qualifies the baseline
  stays. A non-significant large drop is NOT acceptable: missing evidence is not evidence of no loss.
- Sample-size honesty: about 130 paired fields from about 10 documents cannot resolve differences under about 5
  points. Every table prints the paired McNemar p-value and the document-level bootstrap interval, and the
  justification carries that caveat.
- `evalkit/sweep.py` (pure, offline): `SweepPoint(label, run_dir)`; `SweepRow` (accuracy, selective accuracy, coverage,
  row F1, failed documents, cost per document paid and at list price, latency p50/p95, input/output tokens, accuracy
  delta, McNemar `p_worse`, bootstrap interval, M6 verdict) built from `compare_runs` and the scorecard's perf stats;
  `choose(rows, tolerance)` (the rule, exact fractions); `to_markdown` / `to_json` (sorted keys, no timestamps);
  `before_after(...)` for the scorecard section.
- `scorecard.py`: an optional `before_after` field on `Scorecard` (default None), rendered as a "Before / after" section
  in `scorecard.md` and `scorecard.json` when present. `scripts/score.py --baseline RUN` computes it with
  `compare_runs`.
- `scripts/sweep.py`: `--baseline-run DIR` (the "before"), `--sweep-id`, `--split dev`, `--concurrency`, `--tolerance`,
  `--resolution 1024,1568`, `--effort off,low`, `--confirm`, `--dry-run` (prints the plan and the number of calls,
  makes no request), `--resume` (a point whose run.json exists is skipped). Points run through `run_extraction`, one
  run folder each (`outputs/runs/sweep-<id>-<point>`); output in `outputs/sweeps/<id>/{sweep.md,sweep.json}`. A sweep
  refuses zero prices (cost is an axis). Exit codes: 0 done, 1 some document failed, 2 bad arguments or configuration
  (zero prices, missing baseline), 3 the cost cap stopped a run.
- `docs/demo/m8_sweep.md`: the real sweep: table, chosen setting, justification, caveats.
- No change to the extraction pipeline or the prompt.

## Out of scope
- Prompt or validator changes (a different optimization), a model comparison (S3/S5), calibration (next, on the chosen
  setting), the test split, token-cap sweeps, more than 3 levels per knob, Docker (M9).

## Acceptance criteria
Offline and deterministic unless marked.
1. `python -m uv run pytest -q tests/test_sweep.py` -> all pass. Covers: the rule on literal tables (the cheapest
   within tolerance wins; a failed document disqualifies; the exact tolerance boundary; a non-significant large drop is
   rejected; ties by latency; nothing qualifies -> the baseline); delta, p-value and interval taken from `compare_runs`;
   byte-identical markdown and JSON on a second call; the thin-evidence caution under 10 independent documents.
2. `python -m uv run pytest -q tests/test_scorecard.py tests/test_score_script.py` -> all pass, including the
   "Before / after" section and the `--baseline` flag.
3. `python -m uv run pytest -q -m slow tests/test_sweep_script.py` -> passes: the real CLI against the fake server runs
   the points, `--resume` skips finished ones, `--dry-run` makes no request, zero prices exit 2, and the table lists
   every point.
4. `python -m uv run pytest -q -m "slow or not slow"` -> all pass; `python -m uv run ruff check` -> `All checks passed!`
5. `python -m uv run python scripts/sweep.py --baseline-run outputs/runs/dev-baseline --sweep-id m8 --confirm
   --dry-run` -> prints 6 runs x 10 documents (50 planned calls beyond the baseline) and makes no request.
6. [COSTS MONEY ~ $0.25 and about an hour at GLM 5.3 Flash prices; run only after approval, in the background]
   the real sweep on dev: `outputs/sweeps/m8/sweep.md` lists the baseline, 5 points and the confirmatory run, names
   the chosen setting and why; `python -m uv run python scripts/score.py outputs/runs/<chosen> --baseline
   outputs/runs/dev-baseline` shows the before/after table.

## Risks
- GLM is slow (about 2 min per document at the default effort) and the provider's limits are unknown -> concurrency 3,
  one retry, a per-call timeout, resumable points, a dry run first, long runs in the background.
- 10 dev documents are a thin sample -> exact tests, the conservative rule and the printed caveat; no claim under
  about 5 points.
- A cheap setting that fails documents silently looks cheap -> failures disqualify and are a column.
- Price drift (the prices are the provider's page as read on 2026-10-08) -> prices come from `.env` and are printed in
  the report.

## Deviations from roadmap
- "Token budget" is the reasoning effort; one knob at a time plus a confirmatory run, not the full grid (decided with
  the user).
