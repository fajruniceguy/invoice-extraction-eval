# L1: Labeling app - paste rows from a spreadsheet, and the grid that loses the first edit

Status: spec (written before code; not edited after approval)
Roadmap ref: none (tooling needed to finish the test-split labels; requested by the project owner on 2026-10-08)

## Goal
A long line-item table can be entered by pasting tab-separated rows from a spreadsheet, and typing a value into the
line-item grid keeps it the first time.

## Scope
- Bug, as reported: in the `line_items` grid, a value typed once is gone and has to be typed again. Cause found by
  reading `rows_widget` in `tools/label_app.py`: the grid is given `pd.DataFrame(form.rows)` on every rerun, and
  `form.rows` is rewritten from the grid's own output on the same run, so the input of `st.data_editor` changes
  after each edit while its widget state still holds the edit as a delta. The fix is the documented pattern: the
  grid's input is frozen per `rows_version` (kept in session state) and changes only when the version is bumped
  (verify, paste, load). This cannot be reproduced headlessly (`AppTest` does not type into a data editor), so the
  frozen input is tested as a unit and the report says plainly that the browser behaviour is for the owner to confirm.
- Paste box: `evalkit/labeling.py` gets `parse_pasted_rows(text)` (pure). Input is what Excel/Sheets put on the
  clipboard: tab-separated, optional double-quoted cells (a quoted cell may hold a tab or a newline), blank lines
  skipped, an optional header row (`description quantity unit_price amount`, any case, also `qty`, `price`) skipped.
  Columns are `description, quantity, unit_price, amount`, in that order; fewer columns are padded with empty cells,
  more than four is a problem, a paste with no tab at all is a problem (it is not a spreadsheet selection). Cells are
  kept as printed text: the existing `verify rows` step normalizes them with the shared normalizer, so nothing is
  guessed here. A problem leaves the grid untouched and is shown inline.
- `LabelForm.paste_rows(rows, append)` replaces or appends, resets the rows to pending like any other row edit.
  The app shows an expander "Paste rows from a spreadsheet" under the grid with a text area and two buttons
  (replace the rows / add after the last row); a successful paste bumps `rows_version` so the grid shows it.
- `ground_truth/LABELING.md` gets a short "Long tables" section: label every printed row or mark the whole table
  `unlabeled` (never part of it, because the unlabeled rows would be scored as spurious); free-text fields that
  cannot be read may be `unlabeled`; scalar fields are always worth labeling.
- A blind document stays blind: nothing here involves a model.

## Out of scope
- Pasting into the scalar fields, a CSV file upload, changing how rows are verified, scored or saved, the draft flow,
  any label file, the saved work in `outputs/labeling/`, and a redesign of the app.

## Acceptance criteria
Offline and deterministic.
1. `python -m uv run pytest -q tests/test_labeling.py tests/test_labeling_ui.py` -> all pass: the parser on a header
   row, quoted cells with an embedded tab and newline, blank lines, 1 to 4 columns, 5 columns (problem), no tab
   (problem), empty text (problem); `paste_rows` replaces and appends and resets the rows to pending; the frozen
   input does not change when the form's rows change and does change when the version is bumped.
2. `python -m uv run pytest -q tests/test_label_app.py` -> all pass, including: pasting rows fills the grid and the
   form, a bad paste changes nothing and shows the problem, and saved work from before this change still loads.
3. The existing label-app tests and the whole suite stay green: `python -m uv run pytest -q -m "slow or not slow"`
   and `python -m uv run ruff check`.
4. Mutation pass over the parser and `paste_rows` (a mutant of each rule is killed).

## Risks
- The lost-edit bug is not reproduced headlessly -> the fix is the documented Streamlit pattern and is unit-tested at
  its seam; the owner confirms it in the browser, and the paste box is an independent way around the grid anyway.
- The owner is using the app while it is edited -> saved work is written on every real edit, nothing in the stored
  format changes, and a test loads an old saved file.
- Excel puts a trailing newline and sometimes a header on the clipboard -> both are handled and tested.
